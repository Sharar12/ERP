# PROJECT PROMPT: UNIVERSAL ERP MANAGEMENT SYSTEM

## 1. Project Overview

Build a professional, modern, scalable, reusable, and modular Universal ERP (Enterprise Resource Planning) Management System designed to support businesses across different industries.

The system must be flexible enough to serve:

- Manufacturing companies
- Retail businesses
- Wholesale and distribution companies
- Educational institutions
- Healthcare organizations
- Construction companies
- Software companies
- Service-based businesses
- E-commerce businesses
- Corporate organizations
- Small, medium, and large enterprises

The ERP must use a modular architecture where organizations can enable, disable, configure, and customize modules according to their business requirements.

### Technology Stack

**Frontend**
- Next.js (App Router)
- TypeScript
- Tailwind CSS
- Reusable React components
- Lucide Icons
- Recharts

**Backend**
- PHP
- Laravel
- RESTful API architecture

**Database**
- MySQL

# 2. DEVELOPMENT STRATEGY — STRICT ORDER

Development must follow these three phases.

## PHASE 1: COMPLETE FRONTEND DESIGN (MOCK DATA ONLY)

Build the entire frontend experience before starting database development or backend integration.

Requirements:

- Do not create database tables initially.
- Do not implement Laravel initially.
- Do not connect APIs.
- Do not use real backend data.
- Use realistic, interconnected mock data.
- Every page must look functional and complete.
- Every button, dropdown, filter, modal, tab, form, and navigation item must have appropriate frontend interactions.
- Use local mock data and frontend state to simulate CRUD operations.
- The entire ERP must be explorable without a backend.

The objective is to complete a visually impressive, fully interactive ERP frontend before moving to the next phase.

## PHASE 2: DATABASE ARCHITECTURE

After completing and reviewing the frontend:

- Analyze all frontend modules.
- Identify entities, relationships, and dependencies.
- Design a universal relational MySQL database.
- Create migrations, indexes, foreign keys, constraints, and seeders.
- Implement organization-based data separation.
- Support configurable modules and custom fields.
- Ensure the database can support future modules without major architectural changes.

## PHASE 3: BACKEND DEVELOPMENT

After database completion:

- Develop Laravel REST APIs.
- Implement authentication and authorization.
- Implement business logic and validations.
- Connect all frontend modules to Laravel APIs.
- Replace mock data with actual database records.
- Implement role-based permissions.
- Add transaction management, audit logs, notifications, and reporting.
- Test all modules and their integrations.

Never skip this sequence.

# 3. CRITICAL: MOCK DATA IDENTIFICATION & REPLACEMENT STRATEGY

This is a mandatory architectural requirement.

During Phase 1, every mock implementation must be clearly identifiable through source-code comments.

The objective is to make transitioning from mock data to Laravel APIs, another backend, or another data provider extremely easy.

## A. Mandatory Mock Comment Convention

Use consistent comments throughout the entire frontend.

For TypeScript and JavaScript:

```typescript
// MOCK DATA: Replace with API response from GET /api/v1/customers
export const mockCustomers = [...];

// MOCK SERVICE: Currently returns local mock data.
// BACKEND REPLACEMENT: Connect to the customers API.
export async function getCustomers() {
  return mockCustomers;
}
```

For larger mock implementations:

```typescript
/*
 * MOCK IMPLEMENTATION START
 * Purpose: Simulates customer retrieval without a backend.
 * Backend replacement: GET /api/v1/customers
 */

export async function getCustomers() {
  return mockCustomers;
}

/*
 * MOCK IMPLEMENTATION END
 */
```

For JSX/TSX components:

```tsx
{/* MOCK DATA: Replace with real API response */}
<CustomerTable customers={mockCustomers} />
```

For mock configuration:

```typescript
// MOCK CONFIG: Temporary frontend configuration.
// BACKEND REPLACEMENT: Load organization settings from the API.
export const mockOrganizationSettings = {};
```

Use these conventions consistently. Do not randomly mix different mock comment styles.

## B. What Must Be Marked as MOCK?

Explicitly mark all the following:

1. Mock datasets
2. Mock API responses
3. Mock service functions
4. Mock authentication
5. Mock user profiles
6. Mock permissions and roles
7. Mock organization information
8. Mock dashboard statistics
9. Mock chart data

Any information that is temporarily generated, simulated, or hardcoded for frontend demonstration must be identifiable.

## D. Separate Data Access from UI Components

This rule is extremely important.

Never directly import mock datasets inside multiple page components and implement business logic around them.

Instead, create a service/repository abstraction.

Example architecture:

```text
src/
  services/
    contracts/
      customer.service.ts
      invoice.service.ts
      product.service.ts

    implementations/
      mock/
        customer.mock-service.ts
        invoice.mock-service.ts
        product.mock-service.ts

      api/
        customer.api-service.ts
        invoice.api-service.ts
        product.api-service.ts

    config/
      data-provider.ts
```

During Phase 1, only mock implementations will be used.

During backend integration, API implementations will replace them.

The UI components should not care whether their data comes from:
- Local mock data
- Laravel REST APIs
- Another PHP backend
- A different REST API
- Another external data provider

## E. Use Consistent TypeScript Interfaces

Define reusable interfaces independently of mock implementations.

Example:

```typescript
export interface Customer {
  id: string;
  name: string;
  email: string;
  phone: string;
  status: "active" | "inactive";
  createdAt: string;
}

export interface CustomerService {
  getAll(): Promise<Customer[]>;
  getById(id: string): Promise<Customer | null>;
  create(data: Partial<Customer>): Promise<Customer>;
  update(id: string, data: Partial<Customer>): Promise<Customer>;
  delete(id: string): Promise<void>;
}
```

Mock implementation:

```typescript
/*
 * MOCK SERVICE:
 * Uses local data for Phase 1.
 * Replace with Customer API implementation during Phase 3.
 */

export const mockCustomerService: CustomerService = {
  async getAll() {
    return mockCustomers;
  },

  async getById(id) {
    return mockCustomers.find(customer => customer.id === id) ?? null;
  },

  async create(data) {
    // MOCK CRUD: Simulates creating a customer locally.
    return {
      id: crypto.randomUUID(),
      name: data.name ?? "",
      email: data.email ?? "",
      phone: data.phone ?? "",
      status: "active",
      createdAt: new Date().toISOString()
    };
  },

  async update(id, data) {
    // MOCK CRUD: Simulates updating a customer.
    const existing = mockCustomers.find(customer => customer.id === id);

    if (!existing) {
      throw new Error("Customer not found");
    }

    return { ...existing, ...data };
  },

  async delete(id) {
    // MOCK CRUD: Simulates a frontend deletion.
  }
};
```

The API implementation must follow the same service contract.

## F. Data Provider Switching

Create one centralized data provider configuration.

Example:

```typescript
/*
 * DATA PROVIDER CONFIGURATION
 *
 * Phase 1: MOCK
 * Phase 3: API
 */

// Change this configuration to switch implementations.
export const DATA_PROVIDER = "mock" as const;
```

The final architecture should support switching providers without changing page components or reusable UI components.

Do not scatter mock/API conditional statements throughout the application.

## G. Mock Replacement Checklist

Every mock implementation must include:

- `MOCK DATA` comment
- `MOCK SERVICE` comment
- Expected backend endpoint, where applicable
- Expected response or entity type
- Clear replacement instructions

For example:

```typescript
// MOCK DATA
// API REPLACEMENT: GET /api/v1/inventory/products

// MOCK SERVICE
// API REPLACEMENT: ProductService implementation

// MOCK AUTH
// API REPLACEMENT: Laravel authentication endpoint

// MOCK CRUD
// API REPLACEMENT: POST /api/v1/customers
```

Do not leave unidentified hardcoded data in the project.

## H. Phase 3 Replacement Requirement

When Laravel integration begins:

1. Identify every `MOCK` comment.
2. Identify the corresponding service and data source.
3. Implement the actual API service.
4. Preserve existing TypeScript interfaces wherever possible.
5. Replace the mock provider with the API provider.
6. Remove obsolete mock implementations after successful integration.
7. Keep sample data only where it is still useful for tests and development.
8. Verify that all frontend interactions work with real backend responses.

The goal is to avoid rebuilding the frontend when the backend is introduced.
